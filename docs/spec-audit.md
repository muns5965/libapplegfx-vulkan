**S06 discard in the two loop plans** [V]. `air.discard_fragment` is no longer dropped inside `detect_simple_loop` / `detect_guarded_loop`. OpKill splits the block (constant-true OpSelectionMerge + OpBranchConditional) and, when the split block is the plan's entry block, the OpPhi parent label (`id_entry_label`) moves to the continuation block; every other phi parent is a block whose last block is the branching one. `dropped` is always 0 now. Kill vs Demote: OpKill terminates the invocation (no helper lane: derivatives of neighbours are undefined), OpDemoteToHelperInvocation keeps it as a helper (derivatives and later side effects of the helper are suppressed for stores/atomics) [V: SPIR-V spec text]. Tests (lavapipe, kill and demote): `test_discard_loop_plans` (fixtures `spec_discard_{g,p}_{none,entry,loop,merge}`: entry / loop body / merge, conditional per pixel), `test_discard_derivatives` (`spec_discard_deriv`: dFdx/dFdy of a survivor next to a discarded lane = 1.0 under demote). Limitation [N]: Metal's rule for side effects (buffer writes) after a discard is not documented; with OpKill none happen, with Demote they are suppressed for the helper.

## Fix pass 3 (branch research/g7-audit-fix3)
Tags: [V] verified here (test / tool run / quoted spec text), [I] inferred, [N] needs the phone / not documented.

**S06 discard robustness** [V]. New lavapipe test `tests/air2spv-discard-robust-lavapipe.c` (meson: "air2spv discard robustness on lavapipe"); every case runs OpKill (split block) and, where the device enables it, OpDemoteToHelperInvocation, against a CPU reference over an 8 x 8 target. Hand-written fixtures (`gen-discard-robust-fixtures.sh`, spelling `air.discard_fragment` [I]):
- `spec_discard_r_nested`: outer 3 x inner 3 loops (general CFG, block-dispatch lowering) with THREE discards (outer header `i==2 && x<2`, inner body `i==1 && j==1 && x>6`, after the loops `y<1`); survivors compute 9/16, discarded pixels keep the clear. PASS kill + demote, spirv-val ok, no defect.
- `spec_discard_r_diamond`: if/else diamond whose merge block has an OpPhi, discard in the then-arm before the phi's incoming edge. PASS kill + demote.
- `spec_discard_r_imgstore`: discard (x<4) followed by `air.write_texture_2d`: the storage image is written only by the 32 surviving pixels. PASS kill + demote.
- Atomics / device-buffer stores after a discard run from hand-written GLSL (`discard_atomic.frag`, `gen-discard-atomic-spv.sh`; compiled to OpKill, OpTerminateInvocation, OpDemoteToHelperInvocation) because (a) the translator had no atomic instruction at that time (superseded: see "Atomics" below, `atomic_frag_discard` is now translated) and (b) a device-buffer argument cannot be written as an LLVM 18 hand-written fixture: llvm-as writes only opaque pointers and `frag_resource_kind` classifies a buffer by its typed pointee (Apple's AIR is typed), so it is taken for a texture. That tests the DEVICE, not the translator: counter = 32 and only surviving pixels store, in all three flavours on lavapipe.
Kill vs demote, what the specs say [V, quoted]: SPV_EXT_demote_to_helper_invocation: "Any stores to memory after this instruction are suppressed and the fragment does not write outputs to the framebuffer." and "Unlike the OpKill instruction, this does not necessarily terminate the invocation." (atomics are not mentioned there); Vulkan, Shaders chapter, helper invocations: "Stores and atomics performed by helper invocations must not have any effect on memory" (the text excepts Function / Private / Output storage classes), so a demoted invocation's later atomics are no-ops; and the same chapter lets an implementation run OpKill as OpTerminateInvocation OR as OpDemoteToHelperInvocation, so a shader cannot rely on either for neighbouring derivatives (SPIR-V changelog: OpKill deprecated). Consequence: for MEMORY contents the flavours agree; they differ in derivatives of neighbouring lanes (existing `test_discard_derivatives`) and in whether code after the discard still runs (invisible when its stores are suppressed). Metal's own rule for side effects after `discard_fragment()` is [N].

**S04 blit fill: numeric or raw bits?** [V decode, I semantics]. `0x141 FillTextureWithColor` (`blit_inner_ops.c` op_fill_texture_with_color) carries four f64 (r, g, b, a) + `pixel_format` -> `lagfx_translate_blit_fill_texture_color` -> `vkCmdClearColorImage`: a NUMERIC colour like `MTLClearColor`, so `lagfx_fmtcap_clear_color` is the right conversion and stays. Byte / pattern fills are other opcodes that never reach it: `0x140 FillTextureWithBytes` (still `op_ack_stub`: applies nothing), buffer fill 306 (u8 value; `vkCmdFillBuffer` + staging for unaligned edges) and 319 (32-bit pattern) in `arm64_resources.c` (exact bytes asserted in `arm64-exec-blit-unit.c`). `[MTLBlitCommandEncoder fillBuffer:range:value:]` is a byte fill of a BUFFER (the 306 path); Metal has no public texture fill. Verdict: no code change. Regression test `test_blit_fill_vs_clear` (`arm64-render-compat-unit.c`): R32Uint / R32Sint / R8Uint filled through the blit function give the same saturating / truncating result as the render clear (7.0 -> 7, 255.0 -> 255, 5e9 -> 0xffffffff, -3 -> 0 / -3 signed, 300 -> 255 for 8 bit). **S05 research item R1: clip-space compensation for inexpressible viewports** (research only, no code) [I]. Status: a Metal viewport that Vulkan cannot express (beyond `viewportBoundsRange` / `maxViewportDimensions`; counter `viewport_inexpressible`) is a counted skipped draw today. Priority: LOW, tied to occurrence: 0 of 256 captured draws had a non-integral, negative-origin, oversized or otherwise non-default viewport; raise it only when `viewport_inexpressible` is non-zero in real traffic (a phone log line `g7-gpu-vp:`).
Idea: keep a host viewport (x_h, y_h, w_h, h_h) the device accepts (e.g. the render area) and rescale the vertex shader's clip position so the window coordinates equal the guest viewport's. Metal window X = x_o + (x_n + 1) w_o / 2, host X = x_h + (x'_n + 1) w_h / 2; equating gives x' = (w_o / w_h) x + (2 (x_o - x_h) + w_o - w_h) / w_h and y' = (h_o / h_h) y + (2 (y_o - y_h) + h_o - h_h) / h_h (NDC, same y orientation for both viewports, i.e. after the library's existing flip). In clip space (multiply by w_c): x_c' = (w_o / w_h) x_c + ((2 (x_o - x_h) + w_o - w_h) / w_h) w_c, same for y; z and w untouched. Implementation sketch: append to the translated vertex shader's epilogue a load of Position, two fmas with four floats (sx, kx, sy, ky) from a vertex-stage push-constant range, store; the viewport is per draw so the constants cannot be baked; the default path (no rescale) stays byte-identical because the epilogue is only emitted for a pipeline variant.
Semantic problems to settle before any implementation:
1. Clipping. Metal clips at the guest viewport's frustum; after compensation the host clips at the host viewport (the target). What is visible inside the target is the same, but a point / wide line whose centre lies outside the target and inside the guest viewport is clipped by the host (centre-based) while Metal may still draw its extent; guard-band behaviour differs per driver; large |sx| pushes vertices far outside the guard band so more primitives need real clipping. [I]
2. Perspective. The map is affine in (x_c, w_c) and leaves w alone, so perspective-correct interpolation of varyings is unchanged [I: argument, not run]; the cost is precision: x' is formed in fp32 and the viewport transform multiplies it back, so for sx = w_o / w_h >> 1 (or a far-off origin) sub-pixel positions lose bits (about 2^-24 relative to |x'| w_c).
3. Culling. Orientation is preserved while sx, sy > 0 (w_o, h_o > 0 is already required); degenerate-area triangles after rounding may flip or vanish.
4. FragCoord. In exact arithmetic gl_FragCoord.xy equals Metal's window position (same target origin); in fp32 it carries the rounding of item 2, and shaders that branch on `floor(pos.xy)`, fetch with it, or dither with it are sensitive. gl_PointCoord and point size are in window units and unaffected; anisotropic scale (sx != sy) keeps window-space line widths exact only if the rasteriser works in window space (all do).
5. Depth. z / w unchanged; the guest's znear / zfar are a separate, expressible viewport field; depth clip is unaffected. Multiple viewports (viewport arrays), `[[viewport_array_index]]` and mesh / geometry stages are not modelled.
6. Metal's own result for such a viewport is [N] (MTLViewport page: doubles, upper-left origin only), so there is no reference to be faithful to; a lavapipe test would compare against a CPU rasteriser of the guest's mapping.

Lavapipe supports all five (tests: caps equal the ICD's report; fake masks for the rest). Default behaviour is unchanged in spirit: a float atomic is REFUSED at translation (reason `float`) because its AIR spelling was never observed [N], whatever the device supports; `LAGFX_ATOMIC_LENIENT=1` translates float add, and the gate then needs the matching cap. Float load / store / exchange / sub / min / max stay unimplemented.
